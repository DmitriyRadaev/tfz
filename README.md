# Калькулятор ТФЗ

Фуллстек-приложение для расчёта интегрального показателя тяжести токсических
форм зоба. Фронтенд и API живут в одном проекте Next.js и разворачиваются на
Vercel целиком — отдельного бэкенда на Django больше нет, весь его функционал
перенесён сюда.

## Стек

| Слой | Решение | Почему |
| --- | --- | --- |
| Приложение | Next.js 15 (App Router) | Страницы и API в одном деплое |
| База данных | Postgres (Neon) + Drizzle ORM | HTTP-драйвер не держит соединений — подходит serverless |
| Кэш и сессии | Redis (Upstash) | REST-клиент работает из serverless-функций без TCP |
| Аутентификация | JWT в httpOnly-куках (`jose`) | Проверяется на edge, в middleware |
| Пароли | scrypt из `node:crypto` | Memory-hard, без нативных зависимостей |
| Валидация | Zod | Один источник правды для проверок и OpenAPI |

## Устройство

```
src/
  app/
    api/            — route handlers (бывшие Django-вьюхи)
    admin-home/     — административный раздел
    api-docs/       — документация API (замена swagger-ui)
  server/           — серверный код, в клиентский бандл не попадает
    db/             — схема и подключение к Postgres
    auth/           — пароли, JWT, сессии, проверка прав
    http/           — ответы, ошибки, защита от CSRF
    redis/          — клиент и ограничение частоты запросов
    services/       — бизнес-логика и работа с данными
    validation/     — Zod-схемы (бывшие сериализаторы DRF)
    openapi/        — сборка OpenAPI-документа
  entities/         — запросы react-query
  features/         — пользовательские сценарии
  shared/           — API-клиент и UI-кит
drizzle/            — SQL-миграции
scripts/seed.ts     — создание первого администратора
```

## Локальный запуск

Нужен Node 22+.

```bash
npm install
cp .env.example .env.local   # заполните DATABASE_URL и JWT_SECRET
npm run db:migrate           # создаёт таблицы
npm run db:seed              # создаёт главного администратора
npm run dev
```

`JWT_SECRET` можно сгенерировать так:

```bash
openssl rand -base64 48
```

В качестве базы подойдёт и бесплатный Neon, и локальный Postgres: драйвер
выбирается по строке подключения автоматически (переопределяется переменной
`DB_DRIVER` со значением `neon` или `pg`).

Без переменных Upstash локально включается in-memory заглушка Redis — её хватает
для разработки. В продакшене приложение без Redis не стартует: сессии и счётчики
попыток входа разъехались бы между инстансами функций.

Полный локальный стенд с Postgres и Redis в контейнерах:

```bash
JWT_SECRET=$(openssl rand -base64 48) docker compose up
```

## Деплой на Vercel (бесплатный тариф)

1. **Создайте проект.** Импортируйте репозиторий на [vercel.com/new](https://vercel.com/new).
   Next.js определится сам, менять настройки сборки не нужно.

2. **Подключите Postgres.** В проекте → **Storage** → **Create Database** →
   **Neon**, тариф Free. Vercel сам добавит `DATABASE_URL` в переменные
   окружения проекта.

3. **Подключите Redis.** Там же **Create Database** → **Upstash for Redis**,
   тариф Free. Vercel добавит `KV_REST_API_URL` и `KV_REST_API_TOKEN` —
   приложение понимает и эти имена, и «родные» `UPSTASH_REDIS_REST_*`.

4. **Добавьте секрет.** В **Settings → Environment Variables** создайте
   `JWT_SECRET` (минимум 32 символа) для всех окружений.

5. **Примените миграции.** С локальной машины, подставив строку подключения
   к созданной базе:

   ```bash
   vercel env pull .env.local
   npm run db:migrate
   npm run db:seed
   ```

   Для миграций лучше брать прямое подключение без пулера — интеграция Vercel
   кладёт его в `DATABASE_URL_UNPOOLED`. Если `vercel env pull` недоступен,
   скопируйте строку из панели Vercel в `.env.local` вручную и допишите туда же
   `JWT_SECRET` и данные `SEED_SUPERADMIN_*`.

6. **Проверьте деплой.** Откройте `https://<ваш-проект>.vercel.app/api/health` —
   должно вернуться `{"status":"ok","checks":{"database":"ok","redis":"ok"}}`.

Чтобы сократить задержки, в **Settings → Functions** выберите регион рядом с
регионом базы Neon.

## Аутентификация

Вход выдаёт две httpOnly-куки: короткоживущий `access` (JWT, 15 минут) и
`refresh` (7 дней). Токены недоступны из JavaScript, поэтому XSS не уводит
сессию.

Refresh-токен одноразовый: при каждом обновлении выдаётся новый, а старый
удаляется из Redis. Если приходит уже использованный токен — значит он,
вероятнее всего, украден, и все сессии пользователя гасятся. Вместе с номером
поколения сессий в аккаунте это обесценивает и уже выданные access-токены, так
что отзыв срабатывает немедленно.

Отдельного CSRF-токена нет. Его заменяют `SameSite=Lax` на куках и сверка
заголовка `Origin` для всех небезопасных методов — тот же подход, что Next.js
применяет к Server Actions.

## Роли

| Роль | Права |
| --- | --- |
| `WORKER` | Пациенты и расчёты |
| `ADMIN` | То же плюс список сотрудников |
| `SUPERADMIN` | То же плюс создание администраторов |

Первый `SUPERADMIN` создаётся через `npm run db:seed`, дальше администраторов
заводят из раздела «Администрирование».

### Профиль

Клик по аватару в шапке открывает редактирование: ФИО, email и смена пароля.
Email и пароль подтверждаются текущим паролем и завершают сессии на других
устройствах — если учётную запись увели, смена пароля выбрасывает чужого
немедленно, а не ждёт истечения токена.

### Регистрация врачей

Регистрация открыта, но **самостоятельно зарегистрированный аккаунт неактивен**:
войти в систему он не может и данных пациентов не видит, пока администратор не
подтвердит заявку в разделе «Администрирование». Заявки показаны в начале
списка сотрудников.

Так сделано потому, что картотека видна всем аутентифицированным
пользователям: без модерации любой, кто знает адрес сайта, получил бы доступ к
ФИО пациентов, датам рождения и истории расчётов.

Блокировка сотрудника (`Закрыть доступ`) обрывает его активные сессии
немедленно — выданный ранее токен перестаёт работать, не дожидаясь истечения
срока.

## Шкала расчёта

Пороги и веса вынесены из кода в описание шкалы (`src/server/scoring`). Одни и
те же данные используются и для расчёта, и для страницы `/scale`, и для
разбивки «из чего сложился балл» в карточке приёма — разойтись они не могут по
построению.

### Версионирование

Шкала версионируется, каждый расчёт помнит версию, по которой был выполнен.
Это не формальность: без неё рекомендация, выданная полгода назад, перестала бы
быть объяснимой — сохранённый балл не сошёлся бы с разбивкой, посчитанной по
новым порогам.

* версии неизменяемы, правка создаёт новую;
* активная версия ровно одна — гарантирует частичный уникальный индекс;
* старые версии не удаляются: к ним привязаны выполненные расчёты;
* если сумма слагаемых вдруг не сойдётся с сохранённым баллом, интерфейс
  скажет об этом прямо, а не покажет цифры, которые не складываются.

### Редактирование

Доступно только роли SUPERADMIN: изменение порогов влияет на все последующие
клинические решения. Редактируются веса и пороги; состав критериев фиксирован —
на них по именам опирается логика рекомендаций.

Валидация не пропустит шкалу, в которой часть значений осталась бы без балла:
полосы обязаны замыкаться веткой «в остальных случаях», а у последней степени
тяжести не должно быть верхней границы.

Версия 1 создаётся автоматически при первом обращении, отдельного шага
инициализации не нужно.

## Отличия от прежней версии на Django

Логика расчёта перенесена дословно — пороги, веса и формулировки рекомендаций
совпадают. Остальное изменилось осознанно:

* **Пол пациента теперь влияет на результат.** В Django в поле расчёта
  записывался числовой код пола (`0`/`1`), а сравнивался он со строкой
  `"male"` — условие никогда не выполнялось. Из-за этого терялся балл за
  мужской пол и исчезал соответствующий довод в рекомендации по ДТЗ.
* **Даты отдаются в ISO 8601**, а не в формате «ДД.ММ.ГГГГ». Так их можно
  сортировать и сравнивать; под локаль строка приводится в интерфейсе
  (график истории раньше сортировался неверно именно из-за этого).
* **Токены не возвращаются в теле ответа** — только в httpOnly-куках.
* **Роль читается из подписанного токена**, а не из обычной куки `user_role`,
  которую можно было изменить из консоли браузера.
* **Админка Django заменена** разделом `/admin-home`: сотрудники, модерация
  регистраций и создание администраторов. Данные пациентов и расчётов правятся
  из основного интерфейса врача.
* **Правила рекомендаций взяты из клиентского калькулятора, а не из Django.**
  В бэкенде спорные случаи — те, что не попали ни в одну явную ветку —
  завершались ответом «требуется индивидуальная консультация специалиста». На
  случайной выборке он выпадал примерно в половине расчётов. Теперь спорный
  случай разрешается по титру а/т к рТТГ (ДТЗ) или по локализации узлов (МТЗ).
  Шкала баллов при этом не менялась: она сверена с клиентским калькулятором на
  5000 наборов данных, расхождений нет.
* **У МТЗ появилась локализация узлов** (`nodules_bilateral`). В Django такого
  поля не было, и объём операции предлагался одинаковый независимо от того,
  поражены обе доли или одна. Поле обязательно для МТЗ и прямо определяет выбор
  между тиреоидэктомией и субтотальной резекцией.
* **Регистрация стала модерируемой.** В Django `WorkerRegisterView` имел
  `permission_classes = [AllowAny]` и сразу выдавал рабочий аккаунт — то есть
  доступ к картотеке получал любой желающий.
* **Возраст склоняется**: «41 год», «54 года», «25 лет» вместо «41 г.».
* **Пациента и отдельный приём можно удалить** из интерфейса, с подтверждением
  и явным предупреждением о последствиях.
* **Шкала расчёта стала данными, а не кодом**, версионируется и доступна для
  просмотра врачу на странице `/scale`. В карточке приёма видно, из чего
  сложился балл.
* **Цвета сведены в токены** (`src/app/globals.css`) на основе фирменного
  синего СамГМУ `#006CB4`, снятого с логотипа. Раньше по компонентам было
  разбросано 13 несогласованных оттенков.

#### Граница «средней/тяжёлой» степени

Клиентский калькулятор ограничивает эту ветку сверху: `score >= 18 && score <= 40`.
Шкала задумана как 0–40, но фактический максимум выше — стадия ЭОП принимается
до 6, и предельный пациент набирает до 47. У клиента такой случай проваливается
в «спорную» ветку и может получить рекомендацию меньшего объёма, то есть самый
тяжёлый пациент — более щадящую операцию.

Здесь верхней границы нет намеренно (`SEVERE_THRESHOLD` в
`src/server/services/calculator.ts`). Расхождение затрагивает только баллы
41–47. Чтобы повторить поведение клиента буква в букву, верните условие
`score >= 18 && score <= 40`.

#### Удаление пациента

Доступно любому аутентифицированному пользователю — как и в исходном проекте. Оно каскадом удаляет всю историю расчётов; чтобы ограничить
это администраторами, замените `requireUser` на `requireAdmin` в
`src/app/api/patients/[id]/route.ts`.
